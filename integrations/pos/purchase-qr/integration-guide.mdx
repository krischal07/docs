The endpoint is authenticated with the **provider API key** (`Authorization: Bearer <provider_api_key>`, which confirms the POS vendor) plus the **integration key** (`X-Integration-Key`, which confirms the store/outlet). No `webhook_token` is used on this endpoint. The host below is the local dev API (`localhost:8081`); in production it's the Samparka API origin.

## Example curl (success)

```bash
curl -X POST http://localhost:8081/integrations/pos/{provider}/purchase-qr \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <provider_api_key>" \
  -H "X-Integration-Key: <integration_key>" \
  -d '{
    "amount": 1250,
    "currency": "NPR",
    "items": [
      { "name": "Cappuccino", "qty": 1, "price": 850 },
      { "name": "Latte", "qty": 1, "price": 400 }
    ]
  }'
```

### 200 — POS connected + active communication provider → real Wapio QR

```
HTTP 200
{
  "success": true,
  "message": "Purchase QR ready",
  "data": {
    "qr_link": "http://localhost:8081/r/xKd93k",
    "purchase_reference": "ps_1690000000000_ab12cd34ef56",
    "amount": 1250,
    "currency": "NPR",
    "status": "QR_GENERATED",
    "expires_at": "2026-08-31T07:40:08.000Z"
  }
}
```

### 409 — POS integration not connected (status is `CREATED`, not `CONNECTED`/`ACTIVE`)

```
HTTP 409
{
  "success": false,
  "message": "{provider} is not connected for this store",
  "errors": { "code": "pos_not_connected", "status": "CREATED" }
}
```

### 422 — POS connected but no active WhatsApp/Wapio communication provider

```
HTTP 422
{
  "success": false,
  "message": "No active connected communication provider is configured"
}
```

## Behavior matrix

The endpoint only issues a QR when the POS integration is connected **and** an active communication provider exists.

| POS | WhatsApp/Wapio | Result |
|---|---|---|
| Not connected | anything | `409 pos_not_connected` — no QR, no session |
| Connected | not connected | `422 no active connected communication provider` — no QR, no session |
| Connected | connected | `200` real Wapio QR |

## Design choices

| Choice | Rationale |
|---|---|
| Auth via **provider API key (Bearer) + integration key (`X-Integration-Key`)** | Mirrors the canonical ingress. The Bearer key (`spkp_…`) confirms the POS vendor; the integration key confirms the store/outlet. Provider key `slug` must match the route `:provider`. Reuses existing `authenticateProviderApiKey` — no new secrets, no webhook token in the path. |
| **Fresh `purchase_reference` per request (no dedup)** | Because the request no longer carries a `bill_id`, no stable idempotency key exists — each call creates a new `ps_...` session via `buildPurchaseReference()`. Retry-safety therefore lives in the session lifecycle (`ensureQrGenerated`), not across separate requests. |
| **Items are required at creation** (400) | The POS must send product items so the QR session has the bill details needed for loyalty attribution. |
| **`currency` defaults to `NPR`** | POS payloads may omit currency; dashboard uses 3-letter codes, Nepal is the operating market. Explicit value overrides. |
| **POS must be genuinely connected** | The endpoint refuses with `409 pos_not_connected` unless the integration status is `CONNECTED`/`ACTIVE` — matches the dashboard's notion of "connected". A `CREATED`/`DISCONNECTED` integration can't issue checkouts. |
| **Requires an active communication provider** | If the POS is connected but no WhatsApp/Wapio communication provider is active, session creation aborts with `422` (`no active connected communication provider`) — no QR is issued. There is deliberately **no fallback** deep-link. |
| **Only one route addition, placed before the catch-all** | `/integrations/pos/:provider/purchase-qr` is 2 segments, so it never collides with `/:provider/events` (2) or the catch-all `/:provider/:token` (2) — but registered first for safety. |
| **No dashboard/frontend changes** | The POS owns the UI (its receipt). `checkitbro` is a disposable localhost visualizer, not a feature. |

## Open questions to confirm with the team

1. **Idempotency without a bill ID:** each POS request now creates a brand-new session — the same sale called twice produces two sessions/QRs. If the POS can supply a stable sale/receipt reference (or we reintroduce `bill_id`), we can restore cross-request dedup. Is a single source-of-truth per sale required, or is one-QR-per-receipt acceptable?
2. **Duplicate scan handling:** since different requests for the "same" sale are independent sessions, a confused double-scan currently yields one QR per session. Confirm whether a customer-facing dedup (e.g., same phone + outlet + amount window) is wanted.
